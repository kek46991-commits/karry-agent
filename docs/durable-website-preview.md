# ホームページ生成と永続プレビュー

## 修正した原因

1. ホームページ作成は一般ツールループ任せで、HTMLをローカルへ書くだけの回答でも完了できた。
2. `prepare_instant_website` はファイル未保存の段階で `preview.public_url` を返していた。このURLは公開確認・保存前には404となる。
3. 公開確認待ちは10分間のプロセスメモリだけだった。R2へ保存するタスクの実行概要からトレースが除去されるため、画面の再読み込み・再起動後にHTMLや確認操作が復元できなかった。

## 修正後の流れ

`明示的な作成依頼 → 完全なHTMLをモデル1回で生成 → 非公開タスクJSONへ本文とIDを保存 → チャット内で隔離プレビュー → 所有者が内容・公開先を確認 → R2へ公開HTML保存 → 公開URLを表示`

- 明示的なホームページ/Webサイト/HTML作成依頼は、完成HTMLを生成して準備ツールへ渡す専用経路を使用する。URL解析・説明・否定等は既存経路を維持する。
- `write_file` の成功だけで公開URLや表示可能な成果物を捏造しない。
- 未公開の `preview.public_url` は `null`。公開先を確認するための `preview.planned_public_url` はリンクではなく予定として扱う。
- 本文、SHA256、実ファイル名、成果物ID、作成時刻、公開状態を既存の非公開R2/S3タスクJSONへ保存する。DB新設や追加の保存先は不要。
- 保存容量は既存タスクJSONの2 MiB、HTML1件512 KiB、タスクの成果物20件の上限内。保存失敗を「作成・プレビュー完了」としない。
- 再読み込み後は `artifacts` から復元し、確認待ちの10分が切れたりプロセスが再起動したりしても、保存済み本文から新しい確認待ちを作れる。公開同意は保存しない。

## API

いずれも所有者Bearer認証が必要。認証トークンはURLへ付けない。

| API | 内容 |
| --- | --- |
| `GET /api/sessions/{session_id}` | `artifacts` に保存済み成果物のID・状態・ファイル名・取得先を返す。本文は一覧に含めない |
| `GET /api/website-artifacts/{artifact_id}?session_id=...` | 対象タスクに紐付く本文・SHA256・状態を返す。公開前の `public_url` はnull |
| `GET /artifacts/{artifact_id}?session_id=...` | 対象の非公開HTMLを認証付きで配信。無認証の公開リンクではない |
| `POST /api/website-artifacts/{artifact_id}/prepare?session_id=...` | 保存済みの同一本文・ファイル名から公開確認を再発行。モデルは呼ばない |
| `POST /api/agent/websites/confirm` | 既存のSHA256付き明示確認後だけ公開。公開outboxと保存済み成果物の状態を連携 |
| `GET /api/artifacts/{filename}` | 既存の公開済みファイルの実在確認APIを維持 |

新APIの `session_id` はクエリなので、既存の不透明なIDでもパス解釈に混ざらない。`artifact_id` は32桁のランダムID。

## 画面

- 送信中は作成・処理中と案内。保存後はチャット内へ成果物カードを表示。
- 最新の保存済み本文を取得して iframe の `srcdoc` で表示。公開予定URLへ遷移しない。
- iframe は `sandbox="allow-scripts"`（allow-same-originなし）で隔離し、CSPでAPI通信・フォーム・子フレーム等を禁止する。生成HTMLがチャットのトークンやlocalStorageを読まない。
- HTML全文を確認し、端末へHTMLファイルとして保存できる。
- 公開はチェックボックスと公開ボタンによる所有者の確認後。公開URLは保存成功後だけ表示。
- 欠落やストレージ障害はチャット内の案内と再読み込み操作で扱い、404画面へ勝手に遷移しない。
- タスク切替中に遅れて届いた別タスクのプレビューは表示しない。
- 公開済みという過去の記録だけではURLを有効としない。表示・確認時に実体とSHA256を照合し、欠落・破損・公開先変更ならURLを隠して非公開プレビューを残す。公開の再確認は409となり、新しい成果物として作成し直せる。
- 同一ファイル・SHA256・保存先の有効な確認待ちは再利用し、作成と公開再確認で確認枠を二重消費しない。

## 範囲・制約

- 単一HTML（埋め込みCSS/JS）が対象。別ファイルの相対パスに依存する複数ファイルWebアプリ一式のデプロイではない。
- 過去に公開されなかったHTMLや、既に消えた一時ディスクのHTMLを推測して復元しない。修正後に生成する下書きを永続保存する。
- 明示的なmemory/localテストモードは一時保存。本番は既存のs3/R2設定を使い、障害時に一時メモリへ自動復帰しない。
- 成果物の広い公開と、アプリ修正のデプロイは別。今回の本番生成確認は非公開下書きとプレビュー取得だけで行う。

## 検証（実装時）

- Python統合回帰645件合格、2件スキップ（隔離PostgreSQLと作業中に追加されたPR #17画像生成を含む）。DOM34件合格。
- 下書き保存、所有者認証、別タスク、SHA256不一致、再起動相当、確認再発行、キャンセル、公開outbox、同じrequest_idの再送でモデルを再実行しないことをモックで確認。
- TypeScript、Python構文、依存整合性、差分を確認。本番結果はデプロイ後に追記する。
