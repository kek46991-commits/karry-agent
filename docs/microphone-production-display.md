# マイク・シークレットUIの本番表示修正

## 調査結果

2026-10-19、本番 `https://karry-agent-1.onrender.com/` をHTTPと独立ブラウザで確認。PR #24はmainマージ済みで、Renderはe10a64bをliveとして配信していた。2026-10-18のDockerログにはwheelの成功、コンテナ層のexport/push成功があり、ビルド失敗による未反映ではなかった。

両機能は配信HTMLに存在した。シークレットは会話パネルの見出し直下にあり、390pxのスマホではタスク/接続パネル後の下端付近に位置する。未接続・未選択時はdisabledで、非表示ではなかった。利用者が見落とす可能性のある配置と、使用前の案内不足を修正する。

トップレベルの検証ブラウザではHTTPS/getUserMedia/SpeechRecognitionが存在し、マイク権限はprompt、microphone policyは許可。利用者端末の拒否は再現できなかった。旧コードはNotAllowedError、SecurityError、service-not-allowedを一括して「権限が拒否」と案内していたため、原因を分離する。

HTTPのCache-Controlは未指定。空プロファイルでは新UIが見えたため、古いUIがサーバーで固定される証拠はなかった。利用者ブラウザ/WebViewの保持は除外できず、再発防止としてキャッシュ抑止を追加する。

## 修正

- 入力欄の直前へ「🔒 シークレットモード」のスイッチ、ON/OFF表示、接続・タスク選択の案内を配置。ページ上部から入力設定へのリンクも追加。
- rootと`/static/index.html`に`Cache-Control: private, no-store, max-age=0`とPragmaを付け、304再検証応答にも維持する。UI版は`mic-secret-20261019`。
- HTMLへ`Permissions-Policy: microphone=(self)`を明示。同一サイトの本体は許可し、第三者の親iframeの禁止を迂回することはしない。
- 許可方法・通常ブラウザのリンク・許可変更後の再試行を表示。権限denied、埋め込みポリシー、音声サービス拒否、機器使用中、未対応を区別する。
- 実際のマイク要求はユーザー操作時だけ。取得Trackの停止・タスク/モード切替時の停止は維持する。シークレットの無保存分岐・モード隔離は変更しない。

## 利用端末で必要な操作

本番を通常ブラウザのタブで開き、APIトークンで接続してタスクを選ぶ。マイクを押して許可確認が出た場合は「許可」を選ぶ。以前に拒否済みの場合はブラウザのサイト設定、必要ならOSのブラウザ用マイク設定も許可へ変更し、再試行/再読み込みを行う。

親iframeやアプリ内ブラウザがマイクを禁止する場合は、外部ブラウザで開く必要がある。サーバーのコードで利用者の拒否設定を勝手に解除することはできない。Web Speech非対応ブラウザでは手入力を利用できる。

## 検証状況

DOM50件合格。未接続時の描画、モード切替、保存済み拒否からの再試行、iframe制限、サービス拒否、Track停止を検証。HTTP試験でroot/static別名/304のno-storeと新UIを確認。本番モデルの課金呼出し、通常タスク作成・DB/R2への書込みは調査で行っていない。
